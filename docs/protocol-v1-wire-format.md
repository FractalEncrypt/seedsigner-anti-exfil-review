# Anti-Exfil Protocol v1 Multi-Slot Wire Format

Status: frozen protocol v1 (reference semantic/adversarial corpus passed 2026-08-06)
Protocol scope: interactive ECDSA anti-exfil for SegWit v0 PSBT inputs  
Binary message: `AEXB` v1  
QR envelope: `AEXT` v1 in `ur:x-btc-anti-exfil`

This document replaces the single-slot `RungBMessage` layout as the intended
protocol-v1 wire format. The older layout remains only to keep the proven
physical prototype operational during migration. Implementations MUST select
one codec explicitly; the layouts are not interchangeable despite sharing the
experimental `AEXB` magic and version byte.

Normative terms such as MUST, MUST NOT, SHOULD, and MAY are used in their usual
RFC 2119 sense.

## 1. Scope and fail-closed policy

Protocol v1 protects every new ECDSA signature that the participating signer is
expected to add to the supplied PSBT. It supports:

- native P2WPKH;
- P2SH-P2WPKH;
- native P2WSH standard `m-of-n` multisig; and
- P2SH-P2WSH standard `m-of-n` multisig.

Protocol v1 accepts PSBT v0 only. Every non-final input must be one of the
supported SegWit-v0 forms above; transactions mixing supported inputs with
legacy, Taproot, future-witness, or nonstandard inputs are rejected as a whole.
Each input must provide the UTXO amount and script required for authoritative
SegWit-v0 sighash calculation. Nested inputs must provide the exact redeem
script, P2WSH inputs must provide the exact witness script, and all script
hashes must match. If both witness and non-witness UTXO data are present they
must describe the same prevout.

All supported inputs use SegWit v0 signature hashing. Legacy P2PKH, legacy P2SH
multisig, bare scripts, nonstandard witness scripts, Miniscript policies outside
the standard multisig form, and future witness versions are outside v1.

Only explicit ECDSA `SIGHASH_ALL` (`0x00000001`) is supported. A missing PSBT
input sighash field is interpreted as `SIGHASH_ALL` by BIP 174, but the resulting
wire record MUST still encode `0x00000001`. `SIGHASH_NONE`, `SIGHASH_SINGLE`,
`SIGHASH_ANYONECANPAY`, undefined bits, and combinations of those values are
rejected before any opening or signature is emitted.

If the PSBT contains any Taproot input or requests any Taproot key-path or
script-path signature, the entire anti-exfil ceremony MUST fail. A mixed
Taproot/ECDSA PSBT is not partially processed. If any signature expected from
the participating signer is unsupported, malformed, or cannot be represented
canonically, the complete request fails and produces zero openings or new
signatures. There is no ordinary-signing fallback.

Existing signatures from other signers MAY be present in the coordinator's
frozen PSBT. They are context only: SeedSigner MUST NOT return a PSBT, and the
coordinator imports only the exact verified signatures expected from message 4
into its own frozen original.

For the seed selected by the user, the signer enumerates every PSBT BIP32
derivation entry on every non-final input, derives the stated path, and requires
the resulting full public key to equal the PSBT key exactly. Every matching key
that requires a new signature becomes one slot. A pre-existing partial
signature for a key controlled by the selected seed is rejected rather than
silently retained or replaced. A request with no matching new slots is rejected.

## 2. Network codes

The protocol message and outer AEXT envelope both carry the same network code:

| Code | Network |
| ---: | --- |
| `0` | Bitcoin mainnet |
| `1` | legacy public testnet (testnet3) |
| `2` | regtest |
| `3` | signet |
| `4` | testnet4 |

The name `testnet` MUST NOT be used as an ambiguous wire-level alias. User
interfaces may use friendly names, but implementations must distinguish
testnet3 from testnet4 internally and on the wire. A mismatch between AEXT and
AEXB fails the complete request. A signer UI MAY expose one public-test-family
selection because PSBT v0, testnet key versions, address prefixes, and BIP44
coin type do not distinguish testnet3, testnet4, and signet. In that case the
single UI selection accepts codes `1`, `3`, and `4`, preserves the exact
coordinator-supplied code in every response, and still rejects mainnet and
regtest. An implementation whose UI exposes the three public test chains
separately MUST require the exact selected code. Network selection is not
inferred from address text or extended-key version bytes.

## 3. Session and transaction binding

`session_id` is 32 bytes freshly generated by the coordinator CSPRNG for a new
ceremony. It is an opaque identifier, not a hash and not a source of host nonce
randomness.

`psbt_digest` is:

```text
SHA256(exact frozen PSBT bytes carried in messages 1 and 3)
```

The coordinator stores those exact original bytes. Message 3 MUST carry the
identical bytes, not a semantically equivalent reserialization. Messages 2 and
4 carry no PSBT, but repeat `psbt_digest` inside AEXB. The coordinator never
replaces its frozen PSBT with signer-returned data.

The exact expected slot set is part of the transaction binding. Every stage
repeats the slot identifiers, message hashes, sighash types, public keys, and
commitments. Adjacent stages must match byte-for-byte except for their defined
stage-specific fields.

## 4. AEXB header

All integers are unsigned and big-endian. Every message is one header followed
by `slot_count` fixed-length records for its stage.

| Offset | Field | Size | Rule |
| ---: | --- | ---: | --- |
| 0 | magic | 4 | ASCII `AEXB` |
| 4 | format version | 1 | `1` |
| 5 | network | 1 | code from section 2 |
| 6 | stage | 1 | `1` through `4` |
| 7 | flags | 1 | zero; all bits reserved |
| 8 | payload length | 4 | exact total record bytes |
| 12 | session ID | 32 | opaque coordinator session identifier |
| 44 | PSBT digest | 32 | SHA-256 of exact frozen PSBT bytes |
| 76 | slot count | 2 | `1..128` |
| 78 | slot records | variable | canonical order below |

The complete AEXB message is limited to 65,536 bytes. Unknown magic, version,
network, stage, or flags are rejected. Length fields must match exactly;
truncation, trailing bytes, alternate encodings, and zero-slot messages are
rejected.

## 5. Slot identifier, ordering, and limits

One signing slot is identified by the exact pair:

```text
(input_index, signer_pubkey)
```

`input_index` is the zero-based PSBT input index encoded as a uint32.
`signer_pubkey` is the canonical 33-byte compressed SEC encoding of the full
secp256k1 public key. X-only keys and uncompressed keys are forbidden.

Records MUST be sorted by ascending numeric `input_index`, then by unsigned
lexicographic comparison of the 33 public-key bytes. The ordering is strict.
Consequently, duplicate identifiers, exact duplicate records, reordered
records, and two conflicting records for the same identifier are all rejected.

The complete ceremony contains at most 128 slots and at most 16 slots for one
input. Multiple signatures for one multisig input are represented as separate
records. If one seed controls more than one key in that input, each key is a
separate slot. Stage responses MUST contain the complete ordered slot set;
partial subsets and extra slots are rejected atomically.

## 6. Common slot record

Every stage begins each record with the same 105 bytes:

| Record offset | Field | Size | Rule |
| ---: | --- | ---: | --- |
| 0 | input index | 4 | uint32 |
| 4 | sighash type | 4 | exactly `0x00000001` |
| 8 | signer public key | 33 | canonical compressed valid curve point |
| 41 | message hash | 32 | authoritative SegWit-v0 ECDSA digest |
| 73 | host commitment | 32 | `TaggedHash("s2c/ecdsa/data", rho)` |

The authoritative PSBT implementation independently derives the input index,
script, signing public key, sighash type, and 32-byte message hash from the
frozen PSBT. It MUST compare the result with every record before accepting or
producing protocol data. The binary codec validates representation and ordering
but does not replace PSBT semantic validation.

The coordinator generates an independent 32-byte CSPRNG `rho` for every slot.
Reusing one `rho` across slots is forbidden. Implementations MUST detect and
reject duplicate commitments or reveals within a session; a
collision is either an implementation failure or cryptographically negligible.

## 7. Stage-specific records

### 7.1 Message 1: `HOST_COMMIT` (`stage = 1`)

Direction: coordinator to signer.  
Record length: 105 bytes.  
Stage-specific fields: none.

The AEXT envelope MUST contain the exact frozen PSBT. No opening, host reveal,
or signature is present. The signer validates the complete PSBT and slot set
before generating any opening. If one slot fails, it emits no message 2.

### 7.2 Message 2: `SIGNER_OPENINGS` (`stage = 2`)

Direction: signer to coordinator.  
Record length: 138 bytes.

| Record offset | Field | Size | Rule |
| ---: | --- | ---: | --- |
| 105 | signer opening | 33 | canonical compressed valid non-infinity point |

The AEXT envelope MUST NOT contain a PSBT. Every requested slot has exactly one
opening. Signatures and host reveals are forbidden. The coordinator validates
and atomically accepts the complete opening set before emitting message 3.

### 7.3 Message 3: `HOST_REVEAL` (`stage = 3`)

Direction: coordinator to signer.  
Record length: 170 bytes.

| Record offset | Field | Size | Rule |
| ---: | --- | ---: | --- |
| 105 | accepted signer opening | 33 | exact bytes accepted in message 2 |
| 138 | host randomness | 32 | exact slot `rho` matching the commitment |

The AEXT envelope MUST contain the exact same frozen PSBT bytes as message 1.
For every slot, the signer checks the reveal against the commitment and
recomputes the accepted opening before producing any signature. The complete
message is rejected atomically on any mismatch.

### 7.4 Message 4: `SIGNER_SIGNATURES` (`stage = 4`)

Direction: signer to coordinator.  
Record length: 202 bytes.

| Record offset | Field | Size | Rule |
| ---: | --- | ---: | --- |
| 105 | signer opening | 33 | exact opening from messages 2 and 3 |
| 138 | compact signature | 64 | 32-byte `r`, 32-byte low-`s` |

The AEXT envelope MUST NOT contain a PSBT. Message 4 does not echo `rho`; the
coordinator already owns it, and an unnecessary signer-controlled copy would
create another returned field. Compact signatures require `1 <= r < n` and
`1 <= s <= n/2`. DER encoding and the one-byte sighash suffix are added only
when the coordinator imports a verified signature into its frozen PSBT.

For every slot, the coordinator performs both ordinary ECDSA verification and
the anti-exfil opening check. All signatures must pass before any are imported.

## 8. AEXT envelope rules

The existing AEXT v1 framing and canonical CBOR byte-string/UR rules remain in
force, with network code `4` added for testnet4. The outer network and stage
must equal their embedded AEXB fields.

- Messages 1 and 3 MUST carry the exact frozen PSBT.
- Messages 2 and 4 MUST carry no PSBT and an all-zero outer PSBT digest.
- For messages 1 and 3, both the AEXT PSBT digest and embedded AEXB
  `psbt_digest` MUST equal SHA-256 of the carried bytes.
- A response containing a PSBT is invalid and is never sanitized into an
  acceptable response.

## 9. Retry, replay, cancellation, and selective abort

A session has one immutable `session_id`, frozen PSBT, ordered slot set, host
randomness set, commitment set, accepted opening set, and (when complete)
signature set.

Before the coordinator accepts message 2, transport scanning may be retried
with identical bytes. The coordinator MAY explicitly cancel the unused session
and start a new one because no host reveal has been disclosed. Cancellation is
recorded as pre-reveal and is not a selective-abort event.

After accepting the complete message-2 opening set:

- the coordinator MUST persist the session before displaying message 3;
- every retry MUST reuse the exact same PSBT, `session_id`, slot ordering,
  commitments, openings, and per-slot `rho` values;
- the signer must reproduce the same opening for every slot;
- no slot may be retried with fresh randomness or as a smaller subset; and
- transaction mutation, fee bumping, input reordering, key replacement, or a
  nominally new session is not a retry.

Transport failures while showing or scanning an unchanged message do not by
themselves count as signer aborts. Once message 3 has been disclosed, failure
to obtain and verify the complete message 4 is a post-reveal abort. The
coordinator MUST record it durably against the wallet-key identity, retain the
original session for exact retry, and warn the user that repeatedly abandoning
sessions and issuing fresh challenges can create a selective-abort channel.

Replacing the device or restoring the same keys does not reset that history.
An implementation may define escalating UI thresholds, but it MUST NOT erase,
silently reset, or conceal the count. Starting a fresh session after a
post-reveal abort requires an explicit high-severity user action; the abandoned
event remains recorded. Repeated post-reveal aborts require recommending fund
migration to independently generated fresh keys.

Messages from another session, network, PSBT digest, stage, slot set, or
accepted-opening set are replay/substitution failures. Completed message 4 may
be re-scanned idempotently only if every byte and verified signature matches
the completed session.

## 10. Canonical and adversarial test requirements

Before SeedSigner or Sparrow adopts this codec, the shared corpus must cover:

- all four stages for multiple inputs and multiple keys on one input;
- canonical ordering and every duplicate/conflict class;
- maximum counts and over-limit records;
- stage field presence, truncation, trailing bytes, length disagreement,
  unknown version/network/stage/flags, and invalid points/scalars;
- testnet3/testnet4 distinction and outer/inner network mismatch;
- PSBT digest substitution and different message-1/message-3 bytes;
- changed input, public key, message hash, sighash, commitment, opening, reveal,
  signature, slot count, and slot order;
- response PSBT injection and partial response sets;
- unsupported sighashes, legacy scripts, Taproot, and mixed input sets; and
- exact-retry, changed-opening retry, post-reveal abort, and completed-session
  idempotency behavior.
