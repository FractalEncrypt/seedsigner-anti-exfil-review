# Interactive ECDSA Anti-Exfil Protocol v1

Status: cryptographic construction frozen for protocol-v1 vectors  
Wire format: specified in `protocol-v1-wire-format.md`  
Script scope: SegWit v0 ECDSA with explicit SIGHASH_ALL

## 1. Reference construction

The v1 cryptographic construction is pinned for initial vectors to Blockstream Research `secp256k1-zkp` commit:

`2af926dc309a673461f0e2da090105c8f05b4505`

Normative reference files at that commit:

- `include/secp256k1_ecdsa_s2c.h`
- `src/modules/ecdsa_s2c/main_impl.h`
- `src/modules/ecdsa_s2c/tests_impl.h`
- `src/eccommit_impl.h`
- `src/secp256k1.c` (`nonce_function_rfc6979_impl` and `secp256k1_ecdsa_sign_inner`)

This document transcribes the construction so it can be reasoned about and implemented in a terminal reference model. For production cryptography, compatibility is established by differential vectors against the pinned native implementation—not by treating this prose as an independent cryptographic invention.

## 2. Notation

- `G`: secp256k1 generator.
- `n`: secp256k1 group order.
- `x`: valid ECDSA secret-key scalar, `1 <= x < n`.
- `P = xG`: signer public key.
- `m32`: 32-byte ECDSA message hash.
- `rho`: 32 bytes generated by the host CSPRNG and initially kept secret.
- `C`: 32-byte host commitment to `rho`.
- `k0`: deterministic base nonce scalar.
- `R0 = k0G`: serialized 33-byte compressed signer opening.
- `t`: sign-to-contract tweak scalar.
- `k = k0 + t mod n`: final ECDSA nonce scalar.
- `R = R0 + tG`: final public nonce point.
- `sig = (r, s)`: low-S ECDSA signature.
- `ser33(Q)`: standard compressed SEC serialization of non-infinity point `Q`.
- `||`: byte concatenation.

## 3. Tagged SHA256

For an ASCII tag `tag` and byte string `data`:

```text
TaggedHash(tag, data) =
    SHA256(SHA256(tag) || SHA256(tag) || data)
```

This construction uses exactly two tags:

```text
DATA_TAG  = "s2c/ecdsa/data"
POINT_TAG = "s2c/ecdsa/point"
```

The tag strings and byte encodings are case-sensitive and must not be renamed by the transport protocol.

## 4. Deterministic base nonce

The pinned implementation uses libsecp256k1's default RFC6979 HMAC-SHA256 nonce function with:

- secret key `x32`;
- message converted as RFC6979 `bits2octets`, implemented by reducing `m32` modulo `n` and serializing it as 32-byte big endian;
- the 32-byte host commitment `C` as RFC6979 additional data;
- no 16-byte algorithm-name input; and
- an incrementing counter when a candidate nonce is invalid.

Conceptually:

```text
keydata = x32 || int_to_bytes32(int(m32) mod n) || C
k0_candidate[counter] = RFC6979_HMAC_SHA256(keydata, counter)
```

The first candidate satisfying `1 <= k0 < n` is used.

This is not equivalent to `SHA256(x || m || C)` and must not be replaced by that expression.

## 5. Protocol operations

### 5.1 Host commitment

The host generates `rho` from a cryptographically secure RNG:

```text
rho <- CSPRNG(32)
C = TaggedHash(DATA_TAG, rho)
```

The host sends `C`, but not `rho`, to the signer as part of protocol message 1.

### 5.2 Signer opening

For the exact secret key and message hash associated with a signature slot, the signer derives:

```text
k0 = RFC6979_secp256k1(x32, m32, additional_data=C)
R0 = k0 * G
opening = ser33(R0)
```

The signer sends `opening` in protocol message 2. It does not send an ECDSA signature.

The opening parser must accept only canonical 33-byte compressed SEC encodings of valid, non-infinity secp256k1 points.

### 5.3 Host reveal

After validating and accepting the expected opening set, the host sends the original `rho` in protocol message 3.

The host must use the same `rho` associated with `C` and must not replace it after accepting `R0`.

### 5.4 Signer recomputation and signing

The signer recomputes:

```text
C' = TaggedHash(DATA_TAG, rho)
k0' = RFC6979_secp256k1(x32, m32, additional_data=C')
R0' = k0' * G
```

The transport transcript supplies or binds the expected `C` and `R0`. Before signing, the application-level protocol must require:

```text
C' == C
ser33(R0') == opening accepted by the host
```

The native primitive then computes:

```text
t32 = TaggedHash(POINT_TAG, ser33(R0') || rho)
```

The pinned implementation treats `t32` as a secp256k1 tweak and fails in the negligible-probability cases where the tweak is not a valid scalar for public/secret-key tweak addition or produces the point at infinity. It must not silently substitute a different reduction rule in a compatibility implementation.

For a valid tweak:

```text
t = int(t32)
k = (k0' + t) mod n
R = R0' + tG
r = x_coordinate(R) mod n
s = k^-1 * (int(m32) + r*x) mod n
```

The native implementation emits normalized low-S ECDSA signatures. If the calculated signature is invalid under ECDSA's normal rare failure cases, the underlying signing routine advances its nonce counter according to libsecp256k1 behavior. Differential tests must cover the observable result rather than reinterpreting this prose.

The signer sends the signature and the opening required by the wire protocol in message 4.

### 5.5 Host verification

For every expected signature slot, the host:

1. Parses `opening` as `R0`.
2. Computes `t32 = TaggedHash(POINT_TAG, ser33(R0) || rho)`.
3. Computes `R = R0 + int(t32)G` using the same tweak validity rules.
4. Parses the ECDSA signature.
5. Checks `sig.r == x_coordinate(R) mod n`.
6. Performs ordinary ECDSA verification against `m32` and `P`.

Both checks are mandatory. The S2C commitment check alone does not establish that the ECDSA signature is valid.

## 6. Four protocol messages

This cryptographic construction is executed independently for every signature slot `(input_index, signing_pubkey)`.

```text
Message 1: HOST_COMMIT
  public: exact signing context, C for every expected slot
  private host state: original PSBT, rho for every slot

Message 2: SIGNER_OPENINGS
  public: R0 for every slot
  signatures: forbidden

Message 3: HOST_REVEAL
  public: exact signing context, C, accepted R0, rho for every slot

Message 4: SIGNER_SIGNATURES
  public: verified slot identifiers, R0/opening, ECDSA signature
```

The normative multi-slot encoding, exact signing context, session, stages, and
records are defined in `protocol-v1-wire-format.md`. That encoding does not
alter the cryptographic inputs above.

## 7. Required application-level binding

The native API operates on one `(m32, x, rho, R0)` tuple. The air-gapped protocol must additionally prevent tuple substitution by binding every record to:

- protocol version and message stage;
- session/transaction digest;
- input index;
- exact sighash type;
- exact `m32` produced by the authoritative PSBT implementation;
- full signing public key; and
- the expected set of signature slots.

These bindings are transport/application requirements. They are not automatically supplied by the S2C primitive.

## 8. Retry invariant

After the host accepts an opening for a slot:

- it must retain and reuse the exact same `rho`;
- it must require the exact same `R0` on retry; and
- it must not create a fresh commitment/reveal merely because the signer aborted.

The host commitment is included as RFC6979 additional data specifically so the signer can deterministically regenerate a unique base nonce for the same message and commitment without persisting `k0`.

A post-opening abort must be reported to the user and recorded by the coordinator. The coordinator must not conceal it by constructing a slightly different transaction or generating a new `rho`. Replacing hardware while retaining the same wallet keys does not reset the cryptographic concern. Repeated events require an escalating recommendation to migrate funds to fresh independently generated keys.

## 9. Compatibility tests required before implementation use

The terminal reference must reproduce:

- both tagged-hash midstates or equivalent final tagged-hash outputs;
- pinned signer-opening fixtures from `tests_impl.h`;
- at least one complete pinned native anti-exfil signature transcript;
- a changed-message verification failure;
- a changed-host-data commitment failure;
- a changed-signature-`r` commitment failure;
- invalid/off-curve opening rejection; and
- ordinary ECDSA verification in addition to opening verification.

## 10. Protocol-layer resolution

`protocol-v1-wire-format.md` freezes the outer AEXT envelope, exact-PSBT digest,
multi-slot identifiers and ordering, SegWit-v0/SIGHASH_ALL support matrix,
compact low-S intermediate signatures, testnet4 code, and retry/selective-abort
rules. The reference, SeedSigner, Drongo, and Sparrow implementations now share
the frozen vectors and have passed the recorded semantic, adversarial, and
physical prototype gates. Remaining work is independent review and upstream
integration rather than wire-format invention.

The durable retry-journal storage representation and final SeedSigner native
binding strategy remain implementation choices. They may not change `rho`,
`C`, `k0`, `R0`, `t`, the canonical wire bytes, or host verification semantics.
